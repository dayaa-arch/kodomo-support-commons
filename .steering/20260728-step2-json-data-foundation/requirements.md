# Step 2: データ基盤（JSON / 検証 / 静的生成） — 要求

> 関連: [`docs/development-roadmap.md`](../../docs/development-roadmap.md) Step 2 ／ [`docs/architecture.md`](../../docs/architecture.md) ／ [`docs/ideas/initial-requirements.md`](../../docs/ideas/initial-requirements.md)

## 1. 今回の作業の概要

Step 1 で構築したモックデータ駆動の UI を、**実データ（JSON シード）駆動**に置き換える。あわせて、永続的ドキュメントが規定する「正本＝YAML」の前提を**JSON**に改める。

対象データ: [`data/seed/yokohama_support_seed_v0.1.json`](../../data/seed/yokohama_support_seed_v0.1.json)（`schema_version: 0.1.0`、支援機関84件・緊急相談先5件・区マスタ18区・コード辞書・出典カタログ）

## 2. 背景・目的

- 施設情報の正本を実ファイルに移し、`data/` の更新だけでサイトへ反映できる状態にする（管理画面を持たない MVP の前提）。
- ビルド時にスキーマ検証を行い、不正・不足データの公開を防ぐ。
- 「不明な情報を推測で補完しない」原則を、実データ投入時にも守れる形で担保する。

## 3. ユーザーストーリー

- **US-A**: 利用者として、3問に答えると**実在する横浜市の支援先**が結果として表示されてほしい。
- **US-B**: 利用者として、公開情報に無い項目は空欄ではなく「公式サイトで確認してください」と表示され、推測で埋められていないことが分かってほしい。
- **US-C**: 利用者として、区に属さない**市域全体の窓口**も、地域を選んだ後の結果に含めてほしい（見落とさないため）。
- **US-D**: コントリビューターとして、`data/` の JSON を PR で修正すればサイトに反映され、形式を誤ればビルドが落ちて気づけるようにしてほしい。

## 4. 受け入れ条件

### データ基盤
- **AC-1**: 施設情報の正本が `data/` 配下の JSON になり、`data/facilities/*.yaml` への依存が無い。
- **AC-2**: ビルド時にスキーマ検証が走り、**必須項目の欠落・enum 不一致・slug（id）重複**があればビルドが失敗する。
- **AC-3**: 検証は外部バリデータライブラリを追加せず実装する（追加依存を最小限にする方針に従う）。
- **AC-4**: 外部データ（シード JSON）の型・コード値は `infrastructure` の境界でドメイン型へ変換され、`domain`/`application` の公開シグネチャにシードの生の形が漏れない。

### 表示・検索
- **AC-5**: `/facilities/[slug]` が実データ84件分、`generateStaticParams` で静的生成される。
- **AC-6**: 3問ウィザードの検索結果が実データから算出され、件数が「検索結果 ○件」として正しく表示される。
- **AC-7**: 並び順は **選択区 → 市域全体 → 隣接区** の順で、各グループ内は一致度スコアの高い順。
- **AC-8**: シードに存在しない項目（概要・利用の流れ 等）は空欄にせず「公式サイトで確認してください」と表示される。**推測で文章を生成しない。**
- **AC-9**: 区を持たない市域全体の窓口が、結果カード上で選択区・隣接区と区別して表示される。
- **AC-10**: シードにある **住所・電話番号** が詳細ページで確認できる（問い合わせ前に確認したい基本情報のため）。

### 品質・ドキュメント
- **AC-11**: `npm run lint` / `npm run typecheck` / `npm test` / `npm run build` がすべて成功する。
- **AC-12**: マッピング（コード値変換）・スキーマ検証・市域全体を含む検索順序に単体テストがある。
- **AC-13**: 永続的ドキュメントの「YAML が正本」「1施設=1ファイル」の記述が実態（JSON データセット）に合わせて更新されている。
- **AC-14**: 隣接区データがシードに含まれない事実（`ward_adjacency: not_included`）と、コード側マスタで暫定的に保持している旨がドキュメントに明記されている。

## 5. 制約事項

- **プライバシー**: 検索条件を URL / Cookie / Storage / サーバへ出さない Step 1 の実装を維持する。
- **推測禁止**: シードに無い情報を生成・補完しない（`null` のまま「公式サイトで確認してください」）。
- **ランキング禁止**: 閲覧数・人気度による並び替えを導入しない。
- **スコープ外（Step 3 へ）**: 緊急相談先（`emergency_resources`）の実データ接続、Google フォーム URL、アクセス解析。本ステップでは施設データに集中する。
- **スコープ外（Step 4 へ）**: データ件数の拡充・確認状況の格上げ（シードは全件 `official_source`）。
- **再配布の注意**: シードの `data_notes` にある「公開ウェブページは必ずしもオープンライセンスではない」旨は、掲載基準ドキュメント（Step 5）で扱う。本ステップでは技術的な取り込みのみ。

## 6. 明示的に決めた仕様（実装判断）

| 論点 | 決定 |
| --- | --- |
| 正本の形式・粒度 | JSON。**データセット単位の単一ファイル**（`data/seed/yokohama_support_seed_v0.1.json`）を正本とする。将来件数増で分割を再検討 |
| `ward_code` が null（6件） | 「市域全体の窓口」として扱い、`ward: Ward \| null` にする。地域を問わず常に検索結果へ含める |
| シードに無い `summary` | `summary: string \| null` に変更し、未掲載表示に委ねる（推測で書かない） |
| `cost`（44件 null・文字列） | enum（free/partial/paid/unknown）へ写像しつつ、原文（例:「無料（利用登録が必要）」）を `costDetail` として保持 |
| `target_users` の `young_person` / `general_public` | それぞれ `child` / `other` へ写像（Q1 の選択肢に合わせる） |
| `consultation_methods` の `line` / `web_form` / `phone_callback` | 情報を失わないよう、ドメインの `ConsultationMethod` に対応値を**追加**する |
| `verification_status: official_source` | `official-verified`（公式情報確認済み）へ写像 |
| 隣接区 | シードは `not_included`。コード側 `ADJACENT_WARDS` を暫定マスタとして継続利用し、要検証である旨をドキュメントに記載 |
