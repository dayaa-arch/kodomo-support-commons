# Step 1: UI 完成（モックデータ）— 要求仕様

## 1. 背景と目的

`docs/development-roadmap.md` の Step 1 として、実データ基盤やバックエンドに依存せず、モックデータで「よこはま支援さがし」の主要3画面と画面遷移を完成させる。

参考画像 `/Users/shiokawataiga/Downloads/よこはま支援さがし.png` の、安心感のある配色、明確な情報階層、モバイルの質問導線、デスクトップの検索2カラム、縦に読みやすい詳細画面をデザイン基準とする。ただし、永続文書にない「お気に入り」「印刷」は今回の対象に含めない。

## 2. ユーザーストーリー

- 保護者・子ども本人・学校関係者・支援者として、専門知識がなくても3問に答えて支援先候補を確認したい。
- 利用者として、所在地、相談方法、費用、対象者、確認状況を一覧で比較したい。
- 利用者として、施設の詳細情報を問い合わせ前に読みやすく確認したい。
- 利用者として、検索内容を保存・送信されずに安心して使いたい。

## 3. 機能要件

### 3.1 共通 UI

- 「よこはま支援さがし」のブランドマーク、ヘッダー、フッターを全画面で一貫して表示する。
- 色、余白、角丸、影、文字サイズ、フォーカス表示を Tailwind CSS v4 のデザイントークンとして定義する。
- 青を主色、緑・橙・紫を補助色とし、参考画像の穏やかで公共サービスらしい印象を再現する。
- アイコンと簡素なオリジナル SVG イラストを用い、文字だけに依存しない情報階層を作る。

### 3.2 トップ / 3問ウィザード (`/`)

- Q1「誰のために探していますか」、Q2「どんなことで困っていますか」、Q3「どの地域で探していますか」を順番に表示する。
- Q1・Q2・Q3 は単一選択とし、選択状態を視覚とアクセシブルな状態の両方で示す。
- Q1・Q2 の「その他」選択時だけ自由記述欄を表示し、空白のみの入力では次へ進めない。
- 前の質問へ戻って回答を修正できる。
- Q3 完了後、回答をクライアントメモリ上のみに保持して `/search` へ遷移する。
- ヒーロー、進捗表示、安心して利用できる理由、緊急時案内への視覚的な導線を含める。

### 3.3 検索結果 (`/search`)

- 回答済み条件に対し「検索結果 ○件」を表示する。
- 選択区の施設を先にし、その中を一致度の高い順、続いて隣接区を一致度の高い順に表示する。
- 各カードに順位、施設名、運営主体、概要、区名、選択区/隣接区の区別、相談方法、費用、対象/条件タグ、確認状況、最終確認日、詳細導線を表示する。
- デスクトップは左に条件パネル、右に結果一覧の2カラムとする。
- モバイルは1カラムとし、条件パネルを上部ボタンから開閉できる。
- 条件を変更して再検索でき、リセットするとトップの Q1 に戻る。
- メモリ上に回答がない状態で直接 `/search` を開いた場合は、結果を捏造せず、検索開始を案内する空状態を表示する。
- 0件時にも理由と条件変更の導線を表示する。

### 3.4 施設詳細 (`/facilities/[slug]`)

- モック施設ごとに静的な詳細ページを表示する。
- パンくず、施設名、運営主体/部署、イラスト、特徴ラベル、概要を表示する。
- 「何を相談できるか」「誰が利用できるか」「利用までの流れ」「相談方法」「費用」「利用条件」「受付時間」「匿名相談可否」「保護者のみ相談可否」「情報の出典」「最終確認日」「確認状況」を読みやすく表示する。
- 未掲載項目は空欄にせず「公式サイトで確認してください」と表示する。
- モックの公式サイト URL がある施設だけ、外部遷移を明示したリンクを新しいタブで表示する。
- 情報更新報告ボタンと緊急相談セクションは Step 1 の表示モックとして実装し、実運用先への接続は Step 3 に残す。誤利用を避けるためモックであることを明示する。
- 不正な slug は 404 とする。

### 3.5 モックデータとドメインロジック

- 数件の施設モックを `FacilityRepository` ポートのインメモリ実装から取得する。
- 施設、検索回答、区、困りごと、対象者、相談方法、費用、確認状況を strict TypeScript のドメイン型で表現する。
- 横浜市18区と隣接区の静的マスタを共有ドメインに置く。
- 一致度算出、選択区/隣接区抽出、並び替え、特徴ラベル導出、未掲載表示判定を純粋関数として実装する。
- モックデータは表示例であり、実在施設の正確な案内として扱わないことを UI 上で明示する。

## 4. 非機能要件

- モバイルファーストで実装し、390px 前後と 1440px 前後で横スクロールや主要要素の欠落がない。
- WCAG 2.1 AA を目標に、セマンティック HTML、キーボード操作、可視フォーカス、十分なコントラスト、44px 以上を目安としたタップ領域を備える。
- Server Component を既定とし、状態・イベントが必要な最小範囲だけ Client Component にする。
- 検索回答を URL、Cookie、localStorage、sessionStorage、サーバへ保存・送信しない。
- `dangerouslySetInnerHTML` を使わず、外部リンクには `target="_blank"` と `rel="noopener noreferrer"` を付ける。
- UI/アイコン用途の外部ライブラリは追加せず、既存の Next.js / React / Tailwind で実装する。
- Node.js 24 の組み込みテストランナーを採用し、追加のテストランナー依存を増やさない。

## 5. 受け入れ条件

- [x] トップで Q1〜Q3 を回答し、4問目なしで検索結果へ到達できる。
- [x] Q1・Q2 の「その他」は自由記述が必須で、未入力時に分かりやすいエラーが出る。
- [x] 検索結果の件数・カード必須項目・選択区/隣接区の区別・指定順序が正しい。
- [x] 検索結果から条件変更、再検索、リセットができる。
- [x] 有効な施設詳細を表示でき、存在しない slug は 404 になる。
- [x] 詳細の全項目、未掲載時の代替文言、モック外部導線、緊急相談の表示モックが確認できる。
- [x] トップ → 検索結果 → 詳細 → 検索結果の主要導線が破綻しない。
- [x] モバイル1カラム、デスクトップ検索2カラムが成立し、参考画像と整合する情報階層になっている。
- [x] 主要操作がキーボードで利用でき、ラベル・フォーカス・エラー通知が認識できる。
- [x] 検索条件が URL、Cookie、Web Storage、サーバ送信に現れない。
- [x] ドメインロジックの関連テスト、lint、型チェック、ビルドがすべて成功する。
- [x] 実ブラウザでモバイル/デスクトップの画面遷移と表示を確認する。

## 6. スコープ外

- YAML/JSON 正本、ランタイムスキーマ検証、実データの静的生成パイプライン（Step 2）。
- 実運用の公式サイト、Google フォーム、緊急相談先、アクセス解析への接続（Step 3）。
- 30〜50件の実施設データ投入（Step 4）。
- WCAG 適合性監査、性能の最終最適化、公開準備（Step 5）。
- お気に入り、印刷、ログイン、管理画面、ランキング、口コミ。
