# UI の文言・アイコン・重複の改善 — 設計

> 関連: [`requirements.md`](./requirements.md)

## 1. 実装アプローチ

表示に関する判断（どの項目をタグに出すか、どれが未掲載か）は **`facility/domain` の純粋関数**に置き、presentation は結果を描画するだけにする（SRP・テスト容易性）。文言とアイコンの割り当ては presentation 層の定数として整理する。

## 2. 情報設計の原則（重複の解消）

**同じ画面で同じ情報を2度見せない。** 役割を次のように分ける。

| 面 | 役割 | 内容 |
| --- | --- | --- |
| 特徴タグ | ひと目で分かる**確認済みの特徴** | 費用（確認済みのみ）／予約／匿名相談／保護者のみ相談／確認状況 |
| 詳細の表 | タグに出ない**詳細情報** | 何を相談できるか／誰が利用できるか／利用までの流れ／相談方法／電話／所在地／利用条件／受付時間／補足／出典／最終確認日 |
| 未掲載まとめ | 出典に無い項目の**明示** | 上記のうち値が無い項目名を末尾に1箇所で列挙 |

- 事実が確認できない項目はタグに出さない（`unknown` を「不明」というタグにしない）。
- 表に出した項目が空なら、その行は出さず「未掲載まとめ」に項目名を回す。

## 3. ドメインの追加（`facility/domain`）

```ts
// derive-feature-labels.ts
// 変更: 費用が unknown のときは特徴タグに含めない（確認できた特徴のみを出す）

// unpublished-fields.ts（新規）
/** 出典に無い項目のラベル一覧。空欄にせず利用者へ明示するために使う。 */
export function collectUnpublishedFields(facility: Facility): readonly string[]
```

対象項目とラベル: 概要 / 何を相談できるか / 誰が利用できるか / 利用までの流れ / 利用条件 / 費用 / 予約の要否 / 匿名相談の可否 / 受付時間 / 電話番号 / 所在地。

## 5. アイコンの割り当て（重複の解消）

追加: `hand-heart` / `dots` / `backpack` / `cloud-rain` / `coins` / `help-circle`　削除: `sparkles`

### Q1「どなたのために」

| 選択肢 | 現行 | 変更後 | 理由 |
| --- | --- | --- | --- |
| 子ども本人 | `user` | `user` | 変更なし |
| 自分の子ども・家族 | `family` | `family` | 変更なし |
| 学校の児童・生徒 | `school` | `school` | 変更なし |
| 支援している子ども | `users` | **`hand-heart`** | 支える立場を表す。`users` を Q2 に譲り重複を解消 |
| その他 | `sparkles` | **`dots`** | 中立的な記号にする |

### Q2「困っていること」

| 選択肢 | 現行 | 変更後 | 理由 |
| --- | --- | --- | --- |
| 学校に行けない・行きづらい | `school` | **`backpack`** | Q1 の `school` と区別する |
| 気分の落ち込み・不安 | `heart` | **`cloud-rain`** | ハート（好意）ではなく気分の状態を表す |
| 家庭や親子関係 | `family` | **`home`** | Q1 の `family` と区別する |
| いじめ・友人関係 | `users` | `users` | Q1 から `users` が外れるため使用可 |
| 生活や経済面 | `home` | **`coins`** | 経済面を表す |
| 子どもの世話や家族のケア | `shield-check` | **`heart`** | ケアにハートは自然。`shield-check` の意味衝突を解消 |
| その他 | `sparkles` | **`dots`** | Q1 と同じ扱いで一貫させる |

- 重複は「その他」同士のみ（意図した一貫性）。
- `shield-check` は**安全・確認状況の意味に専念**（プライバシー訴求など）。
- トップの3ステップ 2番目は `heart` → **`help-circle`**（Q2 の特定の選択肢と被らない中立記号）。

## 7. 影響範囲

| 領域 | 影響 |
| --- | --- |
| ドメイン | `deriveFeatureLabels` の出力が変わる（既存テストの更新が必要）。`collectUnpublishedFields` を新規追加 |
| 表示 | カード・詳細の情報量が変わるが、**表示できる事実は減らない**（未掲載項目は別枠で明示） |
| データ | 変更なし。`summary` が後日入力されればカード・詳細に自動で反映 |
| プライバシー | 変更なし |
| アクセシビリティ | アイコンは装飾扱い（ラベルは常にテキストで併記）のため影響なし |

## 9. リスクと対応

| リスク | 対応 |
| --- | --- |
| タグから `unknown` を外すと、費用不明が一覧から読み取れなくなる | 詳細ページの「公式サイトで確認が必要な項目」に費用が明示されるため、判断材料は失われない |
| 未掲載項目をまとめると原則（空欄にしない）から外れて見える | 項目名を必ず列挙し、「推測で補完していない」ことが分かる文言を添える |
| 緊急セクションで 110/119 を直書きする | 普遍的で変化しない番号に限定する。施設ごとの窓口データ化は Step 3 で対応 |
